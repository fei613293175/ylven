# 14 高并发、高性能、安全、可观测性与运维

## 1. 性能目标必须分层

“大型专业系统”不是首日部署几十台服务器，而是所有服务无状态可扩容、关键路径有边界、数据结构可演进、指标可观测。首期应在单机或小集群稳定运行，同时具备横向扩容路径。

### 1.1 首期服务等级目标

- 非 AI 普通 API：正常负载下 p95 小于 300ms；
- 创建 AI Run 到连接建立：p95 小于 1s，不包含上游首字时间；
- SSE 自身转发附加延迟：p95 小于 150ms；
- 登录验证码请求：后端处理 p95 小于 500ms，不包含邮件到达；
- 核心 API 可用性目标：99.9%；
- 支付/账本事件不得丢失；
- RPO：核心数据库 15 分钟以内，目标通过 WAL/PITR 接近更低；
- RTO：首期 2 小时以内，商业阶段再提高。

这些是工程目标，不应对个人订阅上游的可用性作无依据 SLA 承诺。

## 2. 部署单元和扩容

1. `ylven-core-api`：用户、项目、文件元数据、商业化、配置；无状态水平扩容。
2. `ylven-ai-runtime`：长连接、上下文编译、模型路由和流式转发；按活动连接、CPU 和事件速率扩容。
3. `ylven-developer-gateway`：公共 API、Key 鉴权、限流和预算；与 App BFF 隔离。
4. `ylven-worker`：按队列类型部署多个 worker pool。
5. `ylven-scheduler`：定时任务，使用租约/分布式锁确保单次执行。
6. `admin-web`、`developer-web`：静态资源通过 CDN，API 走对应后端。

## 3. 数据层性能

### 3.1 PostgreSQL

- 使用 PgBouncer 控制连接数；
- 所有查询有超时和取消；
- 列表使用游标分页，禁止深页 OFFSET；
- 高频条件建立经过 EXPLAIN 验证的索引；
- `usage_events`、`api_request_logs`、`audit_logs` 等大表按时间分区；
- 事务保持短小，禁止在事务内调用上游网络；
- Outbox 与业务事务同库写入，异步发布事件；
- 读副本只用于可接受延迟的报表，不用于钱包强一致判断。

### 3.2 Redis

Redis 用于限流计数、短期会话状态、SSE 事件游标、分布式租约、热点配置缓存和队列辅助，不作为资金事实或永久消息唯一存储。所有缓存必须有 TTL 和回源策略。

### 3.3 对象存储

大文件不经过 Core API 中转。使用预签名直传、分片上传、校验和、生命周期和 CDN。数据库只保存元数据、权限和 object key。

## 4. 流式对话

- 使用 SSE 作为文字流式协议；
- 每个 event 有递增序号，可使用 `Last-Event-ID` 恢复；
- 流式事件短期保存在 Redis/NATS，最终消息合并后写 PostgreSQL；
- 不得每个 token 单独写数据库；
- 客户端断开后根据策略取消上游或继续完成，策略需记录；
- 代理、Nginx 和 Cloudflare 的缓冲与超时必须针对 SSE 配置；
- 心跳不能被计为业务 token；
- 对每个用户、设备、模型和通道设并发限制。

## 5. 上游隔离、熔断和回退

每个供应商/通道独立连接池、并发舱、超时、重试、速率限制和熔断。Claude 限流不能耗尽 GPT 的资源。仅对幂等、明确暂时性错误自动重试；流式已经输出后不得自动换模型拼接回答。

模型故障回退必须透明。用户未授权自动回退时，显示重试或改用模型选择；启用自动回退时，消息元数据必须记录实际模型和回退原因。

## 6. 安全架构

### 6.1 边界安全

Cloudflare 提供 DNS、TLS、WAF、DDoS 防护、Turnstile 和速率限制。源站仅接受 Cloudflare 或受信网络流量；管理后台建议叠加 Cloudflare Access。服务间使用私网、mTLS 或签名令牌。

### 6.2 密钥

所有供应商密钥、Sub2API 管理凭据、SMTP、R2 和数据库凭据只存在服务端 Secret 管理或部署环境，不进入 Git、APK、日志或后台明文。后台显示掩码，并允许轮换与版本记录。

### 6.3 文件安全

文件需 MIME/扩展名双重检查、大小和解压限制、恶意软件扫描、图像重编码或安全解析、沙箱化文档转换。用户文件私有，管理访问有审计。

### 6.4 公共 API 安全

Key 只在创建时显示一次；数据库保存哈希和前缀。支持撤销、过期、IP 白名单、模型权限、预算、并发、RPM/TPM。日志不得记录完整 Key、Authorization、密码、验证码或文件内容。

### 6.5 内容安全

建立可插拔策略：输入/输出风险分类、图片安全、滥用监控和用户举报。首期自用仍需记录安全决策，但不得阻碍正常内部测试。未来商业开放前完成政策、申诉和审计流程。

## 7. 可观测性

### 7.1 统一追踪

每个请求生成 `trace_id`，贯穿 Android 请求、Core API、AI Runtime、Sub2API、Worker 和账本事件。上游 request ID 作为关联字段，不替代内部 trace。

### 7.2 指标

- API QPS、错误率、p50/p95/p99；
- 活动 SSE 连接、首字时间、完整响应时间、取消率；
- 各供应商成功率、限流、熔断状态；
- 队列积压、等待时长、重试和死信；
- PostgreSQL 连接、慢查询、锁、复制延迟；
- Redis 命中率、内存、延迟；
- R2 上传/下载、存储量和失败；
- 支付成功、同步待处理、账本差异；
- 每模型用量、成本和收入。

### 7.3 日志

结构化 JSON 日志，包含时间、级别、服务、环境、trace、用户脱敏 ID、feature ID、错误码和延迟。禁止默认记录用户完整提示词和文件内容；必要调试需短期、授权、脱敏和审计。

### 7.4 告警

告警应对应可操作事件：错误率、供应商认证失效、队列积压、支付同步、余额对账、数据库容量、备份失败、邮件退信和安全异常。每个告警有负责人、严重级别和运行手册链接。

## 8. 备份与恢复

- PostgreSQL 每日全量 + WAL/PITR；
- R2 使用版本、生命周期或跨桶备份策略；
- 配置和基础设施代码进入 Git；
- Sub2API 数据库独立备份；
- 每季度至少一次恢复演练并记录实际时间；
- 备份成功不等于可恢复，必须校验和演练。

## 9. 容量与压测

P12 阶段建立可重复压测：普通 API、SSE 并发、登录挑战、文件直传、任务队列和公共 API 限流。压测不直接调用高成本官方模型，可使用可控 mock upstream，另做小规模真实通道验证。

扩容依据实际指标，不以“未来高并发”为由提前引入 Kubernetes。Docker Compose 是首期部署基线；达到实例、可用区和发布需求后再评估容器编排平台。

## 10. 运维后台

包含服务健康、实例、模型通道、队列、死信、数据库、Redis、R2、备份、任务调度、事故、配置版本、功能开关、灰度、App 版本、日志和追踪。关键运维动作必须权限、原因、审计和可回滚。
