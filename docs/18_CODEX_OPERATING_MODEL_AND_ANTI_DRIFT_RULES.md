# 18 Codex 运行模式与防漂移规则

## 1. 目标

本项目不依靠 Codex 永久记住长对话中的规则。长期规则保持短小，详细需求写入版本化文档和机器合同，交付用脚本校验。Codex 的主要时间必须用于实现、测试和修复，而不是重复检查治理状态。

## 2. 每个新会话的读取顺序

1. 根目录 `AGENTS.md`；
2. `CURRENT_PHASE.yaml`；
3. 对应 `phases/Pxx_*.md`；
4. `contracts/feature-map.yaml` 中该阶段行；
5. 现有 Spec Kit `spec.md`、`plan.md`、`tasks.md`；
6. 与当前功能直接相关的详细文档和代码。

只做一次仓库和环境初检。除非代码或依赖发生变化，不重复运行全仓库 doctor/扫描来代替开发。

## 3. 有效产出要求

每次工作必须产生至少一种：

- 实际代码或迁移；
- 新增/修复的测试；
- 可运行部署配置；
- 明确、具体、可由项目所有者完成的 `OWNER_ACTIONS.md`；
- 证明无法继续的最小阻塞报告。

连续两轮没有代码、测试或具体阻塞产出时，必须停止泛化检查，直接说明卡在哪个命令、文件、接口或外部条件。

## 4. 不得自行改变的内容

技术栈、一级导航、身份流程、数据权威、Sub2API 边界、阶段范围、公共域名、交付合同、财务账本原则。需要改变时先创建 ADR 和变更影响，不能在实现中悄悄替换。

## 5. 外部配置缺失

当需要 DNS、R2、Turnstile、邮件或 Sub2API 密钥时：

1. 创建/更新 `OWNER_ACTIONS.md`；
2. 给出准确字段、来源、配置位置、最小权限和验证方法；
3. 使用 mock、接口抽象或 feature flag 继续完成可开发部分；
4. 只将真实联调标记为 BLOCKED，不将整个阶段停住；
5. 用户提供后立即执行联调，不重新规划。

## 6. Spec Kit 使用边界

- 项目仅运行一次 Constitution；
- 每个实质阶段运行 Specify、Plan、Tasks、Implement；
- Clarify 只用于阶段文档无法解决的关键产品歧义；
- Analyze/Checklist 主要用于身份、钱包、公共 API、安全等高风险阶段；
- Converge 只用于 P13 或明确的阶段收口；
- UI 小修、文案、单一 bug 不新建完整 Spec；
- 不得重复运行 Spec 命令直到得到“完美”文档而迟迟不编码。

## 7. 测试策略

开发期间运行当前模块和受影响测试；阶段末才运行必要全量测试。失败先定位根因，不无上限重跑同一命令。真实上游昂贵或受限时使用契约 mock，并在阶段末执行小规模真实验证。

## 8. 完成声明

Codex 不得仅通过聊天说“阶段完成”。必须执行：

```powershell
.\scripts\05_RELEASE_PHASE.ps1 -Phase Pxx
.\scripts\06_VERIFY_RELEASE.ps1 -Phase Pxx
```

且返回成功。缺 APK、功能清单、测试报告、变更记录、部署记录、构建信息或校验和时，状态仍是 DOING/BLOCKED。

## 9. 新阶段

Codex 不自动进入下一阶段。项目所有者完成 APK 和后台验收后，使用 `CONTINUE_PHASE_PROMPT.md` 开启新会话。这样避免一个会话连续跑十多个阶段后上下文压缩和规则漂移。
