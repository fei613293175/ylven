# 13 产品、套餐、钱包、账本、计费与权益

## 1. 商业系统原则

YLVEN 的商业化数据不能建立在一个可随意修改的 `balance` 字段上。支付、套餐、赠送、AI 使用、图片/PPT 消耗、退款和 Sub2API 同步都必须可追踪、幂等、可对账。用户界面可以显示统一可用额度，但底层必须区分资金来源和有效期。

## 2. 数据权威

- YLVEN：产品、价格、订单、支付、退款、不可变账本、额度桶、套餐、权益；
- Sub2API：实时 AI 调用执行余额/订阅投影、API Key、限流和实际上游用量；
- 上游供应商：原始请求用量和账单证据；
- 每日对账任务：比较三方，不直接覆盖财务事实。

## 3. 产品和价格模型

### 3.1 产品类型

- 订阅套餐：月/季/年或未来其他周期；
- 充值包：增加充值额度；
- 一次性功能包：图片、PPT 或存储额度；
- 管理员赠送：带原因和审批；
- 未来企业合同：不属于首期，但数据模型预留组织和合同价格。

### 3.2 价格版本

价格发布后生成不可变版本。订单引用价格快照，历史账单不得因后台修改当前价格而变化。每个模型使用事件也保存上游成本、销售倍率、最终扣费、币种和价格版本。

## 4. 额度桶

至少三类：

1. `PLAN_CREDIT` 套餐额度：随周期发放，可能到期或重置；
2. `BONUS_CREDIT` 赠送额度：具有来源和有效期；
3. `CASH_CREDIT` 充值额度：由真实付款获得，退款规则独立。

消费顺序由版本化规则控制，默认优先消费最早到期的套餐/赠送额度，再消费充值额度。每次扣减保存具体消耗了哪些桶，便于退款和解释。

## 5. 不可变账本

### 5.1 基本要求

账本记录只能追加，不能直接 UPDATE 删除历史。纠错通过反向分录或补偿分录完成。每个业务事件有唯一幂等键和来源 ID。

### 5.2 关键对象

- `wallet_accounts`：用户按额度类型的账户；
- `ledger_transactions`：一次完整业务事务；
- `ledger_entries`：借贷或增减分录；
- `credit_buckets`：具体额度批次、剩余量和到期时间；
- `balance_projections`：为了高性能读取的投影，可重建，不是财务事实；
- `reconciliation_runs/items`：对账批次和差异。

### 5.3 金额精度

正式金额使用整数最小单位或 PostgreSQL `NUMERIC`，禁止二进制浮点。AI 用量可使用高精度内部单位，展示时再按价格规则转换。

## 6. 订单和支付流程

订单状态：`CREATED`、`PAYING`、`PAID`、`CREDIT_PENDING`、`CREDITED`、`REFUND_PENDING`、`REFUNDED`、`CLOSED`、`FAILED`。

支付回调流程：

1. 验证签名、商户、金额、币种和订单；
2. 使用支付事件 ID 幂等入库；
3. 将订单标记 PAID；
4. 在同一事务创建账本事务和权益发放；
5. 使用事务 Outbox 发布 Sub2API 同步事件；
6. 同步成功标记 CREDITED；
7. 同步失败保持 CREDIT_PENDING 并自动重试；
8. 用户不得因同步失败再次付款。

App、开发者中心、Sub2API 用户页的充值入口都必须进入同一个 YLVEN Payment Center。不得启用两套相互同步的独立支付账本。

## 7. 套餐与权益

套餐包含：AI 共享额度、允许的模型等级、App 并发、API 并发、API Key 数、API 月预算上限、项目数、存储空间、文件大小、图片/PPT 配额、模板权限、记忆和高级功能。

权益使用 `entitlement_code` 统一表达，例如：

- `ai.chat.enabled`；
- `ai.model.tier.max`；
- `developer.api.enabled`；
- `developer.api.key.max_count`；
- `workspace.project.max_count`；
- `storage.bytes.max`；
- `image.monthly.max_jobs`；
- `ppt.monthly.max_decks`。

Android 和后台不能通过套餐名称硬编码行为，必须调用 Entitlement Service 获取有效权益。

## 8. App 与 API 共享额度

App 内部 AI 请求和外部开发者 API 请求归属于同一用户和总额度，但必须分开来源和预算：

- `APP_CHAT`、`APP_IMAGE`、`APP_PPT`；
- `EXTERNAL_API`；
- `ADMIN_TEST`。

开发者 API 必须有独立月预算和单 Key 预算，避免泄漏 Key 耗尽用户在 App 中的全部额度。达到 50%、80%、100% 可配置通知，100% 后自动拒绝外部 API，但 App 是否继续由总余额和套餐决定。

## 9. AI 使用计费

### 9.1 预检和结算

请求开始前检查账号状态、模型权限、并发、预算和估算可用额度。长任务可冻结预计额度；请求完成后根据实际用量结算并释放差额。流式断开不代表上游停止，必须根据最终 provider 结果计费。

### 9.2 使用事件

每个使用事件保存：用户、来源、会话/任务、API Key、模型、供应商、通道、输入/输出/缓存/推理 Token、图片数量、计算单位、上游请求 ID、成功状态、成本快照、销售价、币种、追踪 ID和时间。

### 9.3 失败计费

明确未发送上游的请求不得扣 AI 用量。上游已处理但客户端断开时按实际使用结算。结果不确定时进入 `PENDING_RECONCILIATION`，不能直接重复扣费或无条件退款。

## 10. Sub2API 投影

YLVEN 向 Sub2API 发送幂等命令：确保用户、增加/减少执行额度、同步订阅、模型组、并发和限额。使用记录从 Sub2API 回流 YLVEN。禁止两个系统互相定时覆盖 `balance`。

## 11. 后台菜单

`商业化 / 产品与价格`、`套餐与权益`、`订阅`、`订单`、`支付事件`、`退款`、`钱包账户`、`账本`、`额度桶`、`赠送`、`价格版本`、`使用计费`、`Sub2API 同步`、`对账中心`、`异常补偿`。

敏感动作必须 RBAC、近期认证、原因、双人审批（可按环境开启）、审计日志和幂等。后台不得提供“直接修改余额”按钮，只能创建有原因的调整事务。

## 12. 验收重点

- 重复支付回调只到账一次；
- PAID 但 Sub2API 同步失败不会丢订单；
- 套餐到期只失效对应额度，不误删充值余额；
- 额度消费顺序和 UI 明细一致；
- API Key 预算达到上限后只阻断相应范围；
- 退款通过反向分录可追踪；
- 并发请求不能导致负余额或双花；
- 日终对账能定位差异，不自动篡改历史。
